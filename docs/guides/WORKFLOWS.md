# نظام الموافقات (MVP) + الإشعارات

## الهدف
توفير آلية عامة لاعتماد (طلبات شراء، قيود، فواتير ..) دون تشابك منطق كل تطبيق.

## المكونات
- نموذج `ApprovalRequest` (GenericForeignKey لأي كائن)
- نموذج `ApprovalAction` لتسجيل كل خطوة
- خدمة `create_approval_for(obj, requested_by, amount, reason, required_levels)`
- إمكانية تعدد مستويات (current_level / required_levels)
- إشارة post_save تبث إشعارًا (تم الآن تخصيصه لمستلمي الموافقة المناسبين فقط)
- واجهات ويب: `/approvals/` (قائمة محسنة بجدول Bootstrap) و `/approvals/<id>/` (تفاصيل مع تقدم ومستويات وسجل الإجراءات)
- استهداف الإشعارات الآن يرسل فقط لمن لديهم أدوار `can_approve` ومستواهم مناسب وقيمة المبلغ ضمن حدهم
- حماية إجراء (موافقة/رفض) بحيث لا يمكن لأي مستخدم خارج قائمة المستهدفين التنفيذ إلا لو كان superuser
- مركز إشعارات `/notifications/` لعرض الإشعارات وتعليمها كمقروء مع زر "تعليم الكل"
- شارة عدد الإشعارات غير المقروءة في الشريط الجانبي (context processor `unread_notifications`)

## سيناريو متوقع
1. ينشئ المستخدم طلب شراء PO في حالة "مسودة".
2. يستدعي الكود `create_approval_for(po, user, amount=po.total, required_levels=2)`
3. تظهر في لوحة الإدارة طلب الموافقة.
4. مستخدم بمستوى 1 يوافق (approval_level=1) -> يبقى الطلب "pending" ويرتفع current_level.
5. مدير أعلى (level=2) يوافق -> تتحول الحالة إلى approved.
6. التطبيق الأصلي يتابع (مثلاً يتحول PO من draft إلى approved).

## دمج في التطبيقات
أمثلة لاحقة يمكن إضافتها:
```python
from approvals.services import create_approval_for

if po.needs_approval():
    create_approval_for(po, request.user, amount=po.total, required_levels=2)
```

## توسيع الإشعارات
- الآن: اختيار مستلمين من UserRole.can_approve بمستوى يناسب الطلب (فلترة حسب `approval_level` والحد المالي)
- متوفر: واجهة قائمة + تعليم فردي/جماعي كمقروء + شارة فورية في الشريط الجانبي
- لاحقاً: قنوات WebSocket لبث لحظي، دعم البريد الإلكتروني، تنبيهات متقدمة (تصعيد، تذكير بعد مدة)

## توسيع الأمان
- تحقق صلاحية الموافقة/الرفض الآن يعتمد على دالة مركزية `get_approvers`
- يمكن إضافة Decorator على دوال/فيوهات إنشاء الطلبات لضمان إنشاء الموافقات فقط لكائنات معتمدة
- لاحقاً: تسجيل محاولات رفض/موافقة غير مصرح بها في سجل أمني خاص

## ملاحظات ختامية
الإصدار الحالي يغطي الأساسيات (إنشاء/عرض/تقدم/سجل/حماية/إشعارات). الطريق القادم:
1. دعم ملاحظات/تعليق عند الموافقة أو الرفض (نموذج فوري في صفحة التفاصيل)
2. WebSocket + تحديث الشارة دون إعادة تحميل
3. تكامل API (endpoints) لإدارة الموافقات والإشعارات من تطبيقات خارجية
4. إدارة قوالب نصوص الإشعار (Dynamic Templates)
5. إعداد قواعد تصعيد (Escalation) عند تجاوز مهلة معينة

هذا الأساس تم تصميمه للتوسع دون كسر التوافق.
